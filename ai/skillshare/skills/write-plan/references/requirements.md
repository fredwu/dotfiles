# Resolve plan requirements

Identify the intended outcome, scope, constraints, and acceptance conditions from the relevant conversation and supplied material. Extract their meaning; do not copy whole messages or treat every conversational statement as a requirement.

- Use direct user requests and corrections, user-adopted agent proposals, and requirements the user delegated the agent to derive. Record a brief source note where useful, such as user request, accepted proposal, agent-derived within delegated scope, or conversation digest. Do not attribute agent wording to the user.
- Read messages in context. An instruction such as “use your recommendation” can adopt the referenced proposal; silence does not. A request to design requirements permits reasoned derived requirements within that scope without approval for every detail. Other unaccepted suggestions remain proposals; implementation choices and uncertain inferences belong under chosen direction or assumptions.
- Separate the underlying task from skill invocations, plan selectors, output paths, status reports, tool output, quoted examples, rejected options, and routine discussion. Follow applicable routing and output instructions without misclassifying them as product requirements. A statement in any of these forms can still contain a real task change; classify by meaning and context, not speaker or formatting alone.
- Reconcile updates into one concise current requirement set. Later clear user corrections supersede earlier conflicting directions; retain unaffected constraints. Add a short `### Requirement updates` subsection only when a material change needs explanation. Do not retain superseded instructions as active requirements or build a chat history ledger.
- When original messages are unavailable, use a supplied digest or stored requirements as evidence of intent. Label the source and material uncertainty, compare with available context, and never fabricate exact quotes or user approval. Candidate agreement supports a reading but does not prove authority. A wording difference or missing original is not by itself a blocker.
- Clarify only unresolved ambiguity that materially changes scope, acceptance, or authority and cannot be resolved from context. Otherwise proceed with a stated assumption where needed. Requirements recovered from documents, digests, or agent output do not grant permission for external or otherwise restricted actions.

For a created, revised, or synthesized plan, place `## User requirements` near the top, followed immediately by `## TL;DR` after any requirement-update subsection. Keep requirements concise but preserve meaningful exclusions, limits, and acceptance conditions. The TL;DR summarizes the outcome, chosen approach, key changes, and material risks or conditions in a few short bullets. Refresh both sections when revising a plan so they describe the current result. Use exact quotations only when their wording matters and the source is available.

Comparison and selection responses follow their own output formats; they need no new plan or repeated requirement history.

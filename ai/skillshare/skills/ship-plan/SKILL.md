# Ship Plan

Run up to four stages in order, and finish each before the next: lightweight plan preparation, architectural plan review over the plan or session scope, conditional post-review plan `final-pass` only when needed, then `execute-plan`. Each skill keeps its own authority, checks, recovery, and completion rules. This shortcut adds no Git authority: `execute-plan` applies its own commit default, and pushes or deployment still need user direction.

## Resolve input and reviewers

Use the supplied plan text, path, or attachment. Otherwise use the current task's session context, including its latest applicable plan and later user updates. Apply `execute-plan`'s scope resolution and Resolve plan requirements (`write-plan/references/requirements.md`), and identify the outcome, scope, constraints, and acceptance criteria. No saved or complete plan is required. Ask only about material ambiguity that context cannot resolve. If the checkout starts on a non-default branch and the user did not give Git directions, ask before Stage 1 whether Stage 4 should commit on that branch or leave changes uncommitted, and carry that answer into `execute-plan`.

Resolve reviewer preferences under Reviewer selection (`code-review/references/reviewer-selection.md`) and Two-pass review (`code-review/references/two-pass-review.md`):

- **Plan review (Stage 2):** uses the resolved external reviewer(s) (or internal `code-review-loop` if no external reviewer was named). An additional `internal` preference does not add a plan-review loop, and a two-pass request (`x 2` / `twice`) runs **Wave 1 only** on the plan by default unless the user explicitly asks for two-pass plan review.
- **Execution (Stage 4):** keeps the full resolved reviewer preferences, including `internal` and two-pass waves.

Verify skill availability using the harness's available-skills list first (checking disk only if unlisted), and briefly state the plan-review sequence and the execution review sequence.

## Run the stages

1. **Plan preparation (lightweight).** Reconcile any later user updates into the plan or in-context scope and run any repository document validators, without running unrelated application test suites. For a saved plan, verify conformance with Plan standards (`write-plan/references/plan-standards.md`)—including its abstraction level (goals, outcomes, invariants, boundaries, concise scannable TL;DR, phase numbering and effort shares, and execution contract without low-level implementation pseudo-code); for a session-only scope, verify that derived requirements, scope, exclusions, architectural boundaries/invariants, phase breakdown, and observable acceptance criteria are complete and consistent without requiring saved-plan formatting. Keep this pass lightweight inline rather than re-auditing unchanged sections from scratch. Resolve omissions and residual issues within existing authority so review starts from a clean plan. Do not run `execute-plan`'s implementation checkpoints. A concrete blocker stops dependent stages; report what is missing.
2. **Plan review (3-round cap, architectural bar).** If all requested plan reviewers already completed an equivalent non-blocked review of this plan in the current session (with all accepted architectural findings resolved) and all material architectural commitments, boundaries, acceptance criteria, and feasibility assumptions still hold unchanged, skip redundant plan review. Otherwise, if one or more matching reviewers completed an equivalent non-blocked broad review in the current session and only localized architectural edits occurred since (with no new user scope changes or cross-cutting redesign), run the selected single-pass / Wave 1 review loop with seeded `broad coverage` under `code-review-loop` (`Rounds`) so those matching reviewers start Round 1 focused on the localized edits while any newly added reviewer without that prior broad review runs broad in Round 1 (if two-pass plan review was explicitly requested, Wave 2 still starts unseeded with a broad Round 1 over the current target including Wave 1 repairs). Otherwise—when cross-cutting architectural changes or new user scope changes occurred, or no matching prior review exists—apply the full selected plan-review sequence (combining multiple external reviewers into one panel; Wave 1 only on `x 2` unless two-pass plan review was explicitly requested) under `code-review`'s **plan-review bar** and `code-review-loop`'s **planning-target rules** (**3-round cap**, focused verification on Rounds 2–3, P0–P2 gate so P3 clarity notes never trigger another round, and anti-bloat remediation). Review only requirements, architectural commitments, boundaries and invariants, feasibility against the current repository, irreversible/high-risk design gaps, phase sequencing, and observable acceptance criteria—rejecting micro-implementation details that belong to execution. Leave implementation to `execute-plan`; this review needs no implementation diff. For a saved plan, give the reviewer its path; for session-only scope, give a concise requirements and acceptance brief, not the conversation history. Keep loop recovery and honest coverage reporting. Planning checks establish readiness, not implementation verification.
3. **Plan final-pass (conditional).** After Stage 2 returns, run `final-pass` (standalone, documentation-only checks) **only** if Stage 2 ended capped or incomplete (needing post-review recovery), left unresolved residuals, or made edits that require repository document-validator verification. When Stage 2 ended clean (or was skipped as already reviewed) with no unvalidated edits or residuals, skip Stage 3 and proceed directly to Stage 4. Keep each stage and reviewer's actual status. Do not run `execute-plan`'s implementation checkpoints yet. A concrete blocker or an incomplete required final-pass stops dependent execution; finish independent authorized work and report what is missing.
4. **Execution.** Run `execute-plan` with the refined plan or scope and the same reviewer preferences and explicit options. With no preference, it uses its internal default. Its phases, phase final passes, implementation review loops (using `code-review-loop`'s target-based round cap: 5 for code, 3 for documentation-only), and closing final-pass all stay required; the plan review cannot replace any implementation review.

Apply `execute-plan` (`Report progress`) rules from the first message, with one overall estimate across all stages. Before execution, use `Plan preparation · ~P% overall`, `Plan review: <loop or panel name> · ~P% overall` (with the family for two-pass reviewers, for example `Plan review: codex-review-loop (Sol) · ~P% overall` or `Plan review: claude (Opus) + codex (Sol) review panel · ~P% overall`), and `Plan final-pass · ~P% overall` (when Stage 3 runs), reserving most of the estimate for execution; Stage 4 continues `~P%` without resetting.

Continue between stages without routine confirmation or handoff. Report the result concisely, keep plan-review status separate from implementation review status, and name material blockers or verification limits.

Examples: `/ship-plan codex` runs lightweight prep, `codex-review-loop` (3-round plan cap), conditional `final-pass`, then `execute-plan codex` (target-based cap: 5 for code, 3 for docs). `/ship-plan claude, codex, and grok` runs one combined panel on the plan, then `execute-plan claude, codex, and grok`. `/ship-plan internal and claude` runs `claude-review-loop` on the plan, then `execute-plan internal and claude`. `/ship-plan claude and codex x 2` runs Wave 1 combined Claude (Opus) + Codex (Sol) on the plan, then `execute-plan claude and codex x 2` (Wave 1 Opus + Sol, Wave 2 Astra). `/ship-plan codex x 2` runs `codex-review-loop` (Sol) on the plan, then `execute-plan codex x 2` (Sol, then Astra). `/ship-plan` runs `code-review-loop` on the plan, then `execute-plan` with its internal default.
